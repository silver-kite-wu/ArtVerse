# 知识库重设计实施记录

更新日期：2026-11-01。依据用户已审核并授权实施的知识库合并方案。本文记录实际代码、验证范围和使用方式。

## 1. 本次解决的问题

原确认入口对伏笔结构采用固定字段完整性检查，未知的回收信息也可能阻止确认；分类没有同时限制候选列表，角色卡、关系等标签下出现相同待审内容。原整卡覆盖与同步方式也无法可靠保留人物阶段、资产和来源历史。

现在五种知识类型共用后端 schema、字段校验、事实修订及视角投影。分类与审核状态正交，搜索、数量、分页使用相同过滤条件。延迟返回的旧请求不能覆盖新分类。

伏笔最小结构要求 setup；预计回收章节、回收条件、未知的埋设章节允许空，缺状态规范化为 UNKNOWN。空对象、损坏 JSON、非法类型、跨作品引用仍拒绝保存。已回收或部分回收必须关联实际事件并填写证据，计划不能充当回收事实。错误返回中文字段问题，候选可以先补充再确认。

## 2. 已实现的模块

| 模块 | 实际功能 |
| --- | --- |
| 角色卡 | 参考图和封面、描述、别名、出退场、经历事件、多个境界/等级体系、身份/职务阶段、外物持有及变动；无退场显示 `--` |
| 人物关系 | 有向、对称、反向与平行关系；公开信息/隐情、章节阶段、知道者；图和可访问表格；待审候选虚线预览 |
| 世界观 | 地点、组织、物品、货币、等级体系、规则、历史；稳定实体、限制与代价、适用范围、组织层级、物品实例等字段 |
| 时间线 | 统一事件 ID、人物参与及作用、故事线分栏、叙事/发生顺序、倒叙、相对锚点、时间不确定性、前因和依赖；严格时间依赖防环，显式时间循环例外 |
| 伏笔 | 状态看板/列表、推进线索、埋设与回收事件、证据、作者计划、预计回收窗口、长期未推进提醒；人物、重要度、篇章和窗口组合筛选 |

人物经历、资产变化和伏笔回收引用统一事件，避免复制成彼此无关的记录。退场与已确认死亡分别管理；填写退场不会触发读者角色终止状态。

图支持拖动、缩放、一层/两层人物展开、关系类型/公开程度筛选、点击节点/边详情及 Enter 打开。首屏上限 80 节点、200 边，显示截断和总量；多人物改用稳定网格。移动端默认关系表和知识列表。

伏笔状态通过编辑或新增剧情阶段变更；看板目前没有拖拽跨列功能。事件中的伏笔关联通过伏笔的埋设/回收事件字段建立，目前没有独立的事件侧“相关伏笔”编辑器。

## 3. 数据与写入语义

新增 Flyway `V53__knowledge_facts_and_review.sql`，建立稳定实体、事实、不可变修订、事实实体/事件链接、来源及证据链接、角色图片元数据；扩展候选版本与来源快照，索引片段关联事实修订。沿用 PostgreSQL、JSONB 和现有 pgvector，不引入独立图数据库。

人物引用复用 character_profiles ID，同名人物不会自动合并。非人物通过 knowledge_entities ID 关联。所有引用验证同作品归属；已有实体改名保留 ID，不能直接将已有物品换成地点分类。

一条事实有稳定 ID 和编辑修订；剧情推进保存为新的阶段事实。范围采用 `[from, to)`，截止章节不包含在该阶段。新增阶段可以显式关闭上一阶段；同维度重叠需要先解决。未知范围仅作者可见，不能假设发生于第一章。

人物资料普通编辑保留已有等级、身份、资产及事件关联；事实编辑也同步人物名称、描述与稳定实体名称。正式根只承担兼容投影，事实修订是阶段查询依据。

资产使用精确十进制，前端数量以字符串提交。没有明确期初余额时保持“数量未知”，已知收支单列。业务交易编号去重；完整重试不会重复增减资产或递增版本。转赠双方属于同笔事务；借用/保管与拥有分列，独立装备实例分开统计。

确认对候选和正式基线做版本检查，锁定候选并在同一事务写入正式知识、修订、候选状态和索引任务。失败整体回滚，索引仅在提交后派发。旧索引任务不能替换新根版本的片段；无可用向量索引时仍使用结构化事实浏览及召回。

## 4. 章节、来源和历史

来源章节、首次揭示章节、故事发生时间、阶段有效范围分别存储。候选保存抽取时的源快照与哈希；源变更或目标版本变更返回 409，要求重新比较，不能批准未展示的新版资料。候选源只归属于本次改动，不将新源误挂到旧等级事实。

章节视角统一过滤列表、计数、搜索、人物名称和图片、图边及标签、事件引用和召回片段。未来结束章节和未来回收事件不出现在早期投影；作者私密回收计划只在作者视图显式展开。读者角色快照额外检查已发布章节和 known_by，不注入最新整张人物卡或原始整章；群聊按各回复角色自己的认知取事实。

来源和历史可在详情展开，来源章节可跳回编辑器；修订恢复会保存为新版本。单章删除遇到知识历史/图片引用返回中文冲突，需先整理引用。整部作品删除按依赖顺序释放历史链接，避免章节外键阻止清理。

## 5. 旧资料与迁移

V53 已在本地真实数据库执行，后续结构变更应新增迁移，不能编辑已执行的 V53。部署前按现有流程备份数据库并让 Flyway 管理迁移，继续使用 `ddl-auto: validate`。

旧知识保留为 LEGACY_UNSCOPED，不推测其过去阶段。作者可查看并逐步补充范围；未整理前不进入章节自动上下文。旧角色卡缺少 JSON character_id 时根据已有 profile 外键适配，不凭姓名合并。已有图片复用合法对象键登记元数据，不重复上传。

旧数组接口及无请求体 approve 入口保留；新页面采用独立 browse DTO，并提交版本。兼容不意味着旧的无效结构可跳过新校验。没有自动对用户作品执行全书重抽取或批量调用外部模型，也没有批量重建收费向量。

迁移测试在带旧卡片的 V52 数据库升级到 V53，验证内容、关联、作者投影和范围标记，随后重新执行迁移验证零新增。

## 6. 使用方式

1. 从作品编辑器打开知识库，选择角色卡、人物关系、世界观、时间线或伏笔，再选择正式/待确认等状态。搜索与章节视角共同生效。
2. 待确认记录点击进入审核，阅读来源与问题，补充中文表单后确认。高级 JSON 必须显式应用；损坏内容不会覆盖表单。更新既有记录时选择目标并核对差异。
3. 角色卡中“编辑档案”修改基本信息；“新增事实 / 剧情阶段”记录境界、身份、外物变化。剧情推进选择结束上一阶段，纠错选择具体事实的“修订”。
4. 在角色卡管理参考图、封面、说明和适用阶段；没有揭示章节的图只在作者视图显示。出场、退场、未知数量均可留空，显示占位不写入数据库。
5. 时间线添加事件和参与人物后，角色经历自动关联。切换故事发生顺序可以查看倒叙事件，章节视角仍按实际揭示范围过滤。
6. 伏笔先录入 setup，再逐步添加线索与阶段。预计窗口属于计划；实际回收必须给出事件和证据。全书作者视图可以按窗口筛选，章节视图不展示该私密筛选信息。
7. “知识工具”提供当前章事实召回预览及索引重建；界面区分结构化事实与向量配置，保存不等待向量服务。

## 7. 代码和 API

后端核心为 `application/knowledge/KnowledgeSchema`、`KnowledgeFactService`、`KnowledgeProjectionService`；审核和索引接入 `KnowledgeCandidateService`、`KnowledgeService`。抽取约束及 novel/manga common-rules 同步更新。

前端位于 `frontend/src/components/knowledge/`，包含 workspace、typed form、review、fact editor、detail、graph 和 module views；`frontend/src/api/knowledgeWorkspace.ts` 显式规范新旧命名字段。

所有 API 位于 `/api/stories/{storyId}/knowledge`，继续检查登录与作品归属。

| 路径 | 用途 |
| --- | --- |

| GET /browse、/overview | 类型×审核状态、搜索、模块筛选、分页与同条件计数 |
| GET /units/{unitId} | 指定视角的正式知识 |
| GET /characters、/characters/{characterId} | 聚合人物卡及阶段、资产、经历、参考图 |
| GET /relations/graph | 有界图、候选预览、人物一/两层展开 |
| GET /events、/foreshadowing | 时间线及伏笔聚合投影 |
| POST /entities | 创建非人物稳定实体 |

## 10. 交付边界

本地实现和上述回归已完成。未执行公开发布、云部署、全书自动重抽取或生产索引重建。来源内容的语义冲突仍依赖作者审核与新阶段/修订处理，没有增加自动判断所有世界规则矛盾的推理引擎。

部分聚合查询目前在作品事实加载后进行过滤，大型作品需结合真实数据进一步优化 SQL 和分批接口。没有把本次 85 人物样本外推为任意规模性能保证。现有工作树包含其他功能的大量用户修改，本次未回退这些修改，也未自动提交或推送。

## 11. 文本表单与 JSON 兼容修复（2026-11-01）

问题复现：实际候选 #53 的 limits 是单元素数组，costs/exceptions 是空数组，而 schema 将这三个字段定义为选填文本，导致作者未填错内容也被格式检查阻止。旧表单还会通过 `String(value)` 将对象展示为 `[object Object]`。

处理方案及实现：

- 普通文字表单是默认入口。多条内容用换行，未知选填项留空，由 API 自动序列化 JSON 存储；作者无需处理结构代码。
- 后端 `KnowledgeSchema.normalizeField` 统一兼容读取和保存。文本数组按行连接，空数组/空对象/空白文字转换为空值；对象将键和值转换为可读分行文字，不推测剧情。普通文字和无法解析为 JSON 容器的括号正文原样保留。字符串列表字段兼容逐行文字和 JSON 字符串数组。
- 候选详情、候选列表和正式聚合读取均使用相同规则，旧记录无需迁移或重新抽取；读操作不写回候选、不改变版本。保存补充、确认和事实修订按规范类型持久化，原来源快照及既有历史保留。
- 前端 `knowledgeFormValues.ts` 为普通字段和可选高级导入提供统一转换。有效 JSON 应用后回填可编辑文字；文本框直接粘贴 JSON 容器也在离开输入框时转换。导入失败保留已填表单，并用中文说明可以继续普通编辑。
- 人物、章节、事件 ID、枚举、数量等不进行含义猜测；非法引用仍严格拒绝。未知扩展字段保留，对象展示为键值文字，避免 `[object Object]`。
- 抽取提示明确文字字段为字符串或 null、多条用换行，减少新候选再次生成不同格式。本轮没有新增/修改数据库迁移。

验证：后端编译和 36 项定向测试通过（schema 8、真实 PostgreSQL 集成 22、抽取 2、作品服务 4），前端转换测试 5 项通过，lint/build 通过。新增真实事务用例覆盖旧数组候选无需编辑即可批准、JSON 导入与文本修改使用相同持久化类型。真实浏览器 8 项检查通过，含规定账号、旧候选读取、文字与 JSON 往返、损坏导入保护及清理。证据为仓库根目录 `output/playwright/knowledge-form-compatibility-report.json` 和 `knowledge-text-form-roundtrip.png`。

候选 #53 在首次检查时为 PENDING v2，三个字段错误已消失；回归期间既有后台章节抽取任务生成新候选，它随后进入 SUPERSEDED v3。本轮没有对真实候选提交编辑或确认。临时作品 107 经正常接口删除，数据库作品、知识根、事实、实体残留均为零。浏览器有会话恢复时的一次401及删除临时作品时在途读取的404，没有未捕获 JavaScript 异常。
