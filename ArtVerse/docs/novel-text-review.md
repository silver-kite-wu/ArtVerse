# 小说文字修改审阅

## 目标与交互

作者的正文相当于开发者的源代码。请求“优化／润色／修改本章”后，AI 应准备可以审阅的正文变更，作者确认的文本才进入章节版本历史。

1. 请求前沿用编辑器的自动保存，模型读取当前章节及版本。
2. `POLISH` 使用 `STORY_CHAT_WRITE` 工具集及文笔润色业务技能。模型向 `draft_novel_content` 提交完整正文快照，分析、诊断、改动说明留在聊天中。
3. 正文主区域进入审阅：段落级红删绿增，字符级高亮，显示原文和草稿行号；较长未改内容可以折叠，上一处／下一处按钮定位变化。
4. 默认采纳全部建议；可逐处保留原文、全部采纳或全部保留，也可以进入“编辑最终稿”直接修改。手工编辑后明确标注，对比仍展示原始 AI 建议；返回逐处选择需确认清除手工编辑。
5. “确认并保存新版本”提交最终稿，成功后更新编辑器，再将真实审阅结果交回原 Harness 会话继续总结。放弃保留原文并继续总结放弃结果。空文、超过五万字、与原文相同或基准版本过期时不可确认。

手机端从助手卡片点击“审阅修改”会收起覆盖式助手抽屉。正文差异独立滚动，底部确认操作保持可见。浅色和深色主题共用语义颜色。

## 保存契约

`POST /api/chapters/{chapterId}/story-chat/conversations/{conversationId}/runs/{requestId}/artifacts/{artifactId}/decision`

请求字段：`decision`（`confirm` / `discard`）、`content`（完整最终稿）、`base_version`、`expected_content_hash`（原始 AI 草稿的指纹）、可选 `continue_agent`。章节编辑器传 `continue_agent: true`；省略时保留旧调用方的保存即完成行为。

确认是服务器直接执行的作者操作，不再次调用模型，不要求模型配置或模型执行租约：

- 校验作者、会话、请求、草稿的归属和类型；先锁运行，再锁草稿和章节。
- 校验原始草稿指纹及基准版本，所有正文保存仍调用 `NovelContentService` 校验当前章节版本、字数并建立历史版本。
- 草稿 payload 保留 `content` / `content_hash` 和 `base_content`，另存 `reviewed_content` / `reviewed_content_hash`，可追溯 AI 原稿与作者最终稿。
- 相同最终稿的重复确认返回已提交结果，不重复建版本；不同最终稿或反向放弃已提交草稿返回冲突。重复放弃幂等。
- 仅允许等待确认、已成功或已失败的运行中的有效草稿被审阅；后两种兼容旧任务在生成草稿后结束的状态。运行中、取消、被中断的任务不能确认。恢复旧草稿也必须通过章节版本校验。
- 默认兼容流程在同一事务中记录助手结果并完成；已有终态不被复活。`continue_agent: true` 则先保存正文及 `runAttributes.review_result` 回执、记录 `review_saved`，暂留 `WAITING_USER`，提交后再请求继续总结。版本冲突等失败回滚提交，不把草稿标为已提交。

模型未调用 `ask_user` 但已产出有效草稿时，服务端主动持久化 `WAITING_USER` 并发出审阅中断；未产出草稿则报告失败，不宣称优化已完成。模型请求的章节版本通过 `NovelDraftBaseContext`、签名 MCP 执行凭证及远程 RuntimeContext 传至草稿工具，防止生成期间正文变化后仍以新版本标记旧内容。

## 审阅后继续 Harness

编辑器保存成功后调用现有 AG-UI resume 接口，`decision: reviewed` 并携带同一 `artifact_id`。服务端锁定运行，验证已提交回执、草稿归属和状态，再从该运行的 `external_exec_required` 日志取得原 `ask_user` 工具调用 ID，向相同的 `STORY_CHAT_WRITE` Harness session 送回 `ToolResultBlock(SUCCESS)`。该工具结果包含保存回执及当前实际正文，覆盖作者手动编辑的内容；完整正文不重复放入公开活动日志。

继续阶段只提供 `get_novel_context` 业务工具，并要求总结实际审阅结果，不能再次生成草稿、保存或安排任务。`review_resumed` 来源于 AgentScope 的实际 `ExternalExecutionResultEvent`，不能用前端静态消息替代恢复证据。最终回复更新同一 request 的助手消息，暂停及异常时保留 `PARTIAL` 内容。

保存成功与总结成功是两个结果。总结失败不回滚正文；回执保留，可点击“继续生成审阅总结”，刷新后也能恢复此入口。重复恢复成功运行返回已有结果，执行中的重复恢复返回冲突，取消的任务不能恢复。总结重试不调用保存接口，不重复建立正文版本。

恢复前先将运行状态 flush 为 `RUNNING`，再进行 JDBC 租约领取及实体刷新，避免旧 `FAILED` 状态误报租约冲突，或刷新丢失新的运行状态。原外部审核结果已经由 Harness 接收时，重试不重复注入该工具结果。上游 HTTP 402 明确提示检查模型账户余额或配额，用户处理后可手动继续总结。

## 章节身份、执行记录与错误

- `chapter_id` 是数据库资源 ID，`chapter_number` 是作品内章节序号；例如资源 6 可以是第 1 章。初始上下文和读取结果都包含二者及 `chapter_display_name`，工具仍使用服务端绑定的资源 ID。正文和召回材料仅作为参考数据。
- 实时与历史事件共用前端 reducer，展示真实模型处理阶段、工具状态、工具耗时和审阅/保存/继续结果；不展示模型内部推理原文。工具调用按 run 和原工具调用 ID 归并，历史恢复不会覆盖更新的实时状态。
- 后端现有 `CUSTOM` 事件（包括 `artverse.tool_audit`）接入聊天面板；确认结束后刷新持久化活动记录，页面刷新后恢复最近 30 次运行。
- 小说读取、草稿、保存及人工审核工具的活动结果使用字段白名单，只包含章节、版本、草稿状态等元信息；原始工具结果仍完整交给模型。其他漫画工具契约不变。
- `StoryChatFailure` 区分上游 HTTP 错误、业务拒绝和执行阶段错误；不把上游响应正文、提示词或密钥放入公开错误。前端兼容错误体 `message` / `detail` / `error`。
- 出错保留已收到的回复、执行记录与审阅稿。传输提前结束先查询同一运行状态，再从当前持久化游标接续事件；重连不重新发起模型或写入。无法核实状态时明确提示刷新核对。
- 无参 MCP 工具声明 object schema；`ask_user.options` 明确为 string 数组。此处规范化解决契约缺口，但不能据此认定原始 HTTP 400 的唯一根因。

无数据库迁移；新增快照及审阅字段保存在已有 artifact JSON 中。旧草稿缺少 `base_content` 时以前端当前正文回退显示，基准版本过期依然禁止写入。原有 Agent resume 接口保留供其他调用方使用，章节编辑器已切换至独立 decision 接口。

## 差异计算与草稿边界

`novelDiff.ts` 按保留换行的行序列计算差异；连续增删合并为一处修改，字符级比较使用 Unicode code point。行级与字符级 LCS 矩阵分别限制为一百万、十六万单元；超限以整块替换展示，保留共同前后文，避免长章节占用无界内存。它不提供语义句子匹配或移动段落识别。

作者的逐处选择和手工最终稿保存在当前浏览器组件内；刷新或离开会提示，返回可恢复服务器的 AI 原始草稿，本地选择及手工编辑不会跨刷新恢复。

## 本地接口生效与错误排查

新增 `decision` 接口后，需要重启后端。`mvn compile` 只更新 class 文件，不会让已运行的 Spring 实例自动注册新路由；前端 Vite 则会立即更新，因此可能出现前端按钮已切换、后端仍没有对应接口的情况。

2026-11-01 的保存错误日志为 `NoResourceFoundException`，请求没有进入确认保存代码。原因是 17:57 启动的进程未加载 18:24 编译的新接口；它被通用异常处理误报为 `Internal server error`。`GlobalExceptionHandler` 现在将缺失接口／资源准确返回 404，并由回归测试覆盖静态资源兜底和无 handler 两种路径。

重启后可对完整 decision 路径发送 `OPTIONS`，验证 `Allow` 包含 `POST`；这不会保存或放弃草稿。待审阅草稿保存在数据库中，重启不需要重新生成；刷新前应注意当前逐处选择与手工最终稿仅保存在浏览器组件内。

本机 Docker 的旧客户端协议兼容参数为 `-Dapi.version=1.44`。使用本地已有 PostgreSQL 镜像且无法下载 Ryuk 时，可以仅对本次测试设置 `TESTCONTAINERS_RYUK_DISABLED=true`；测试容器仍由 JUnit 生命周期停止，异常退出后需检查并清理遗留的测试容器。
