# Scheduled manga generation implementation

## Scheduling decision

The application uses AgentScope Harness 2.0.4, but the current `pom.xml` has no AgentScope Scheduler extension. The available scheduler documentation in the feature design does not establish that this version supports absolute one-shot registration with persistence, cancellation, and cross-instance ownership. This implementation therefore uses a PostgreSQL-backed polling trigger (`artverse.scheduled-manga.poll-interval-ms`, default `5000` ms). Polling only finds due task IDs; an atomic conditional update claims each task and gives it a lease and fencing counter. Future tasks remain in PostgreSQL across restarts. This is a one-time `requested_at` timestamp, not CRON.

## API

- `POST /api/chapters/{chapterId}/scheduled-manga` creates a task. Requires `Idempotency-Key` (maximum 128 characters); body: `{"localTime":"2026-10-22T00:00:00","timezone":"Asia/Shanghai","model":"optional-model","configId":123}`. `timezone` is optional and defaults to `artverse.scheduled-manga.default-timezone` (default `Asia/Shanghai`, override with `ARTVERSE_SCHEDULED_MANGA_TIMEZONE`). At most `artverse.scheduled-manga.max-active-tasks-per-user` active tasks are accepted per user (default `3`); each task snapshots at most 60 missing panels. Response includes `task_id`, state, UTC `scheduled_at`, resolved `local_time`, timezone, chapter ID and missing panel count.
- `POST /api/stories/{storyId}/scheduled-manga` creates one task per explicit chapter number. Body uses the same fields plus `chapterNumbers`, an array of one to three chapter numbers in that story. The request is atomic and returns all persisted task IDs.
- `GET /api/chapters/{chapterId}/scheduled-manga/{taskId}` returns task state and per-panel state, attempts, result image ID and safe error summary.
- `GET /api/chapters/{chapterId}/scheduled-manga/{taskId}/events` streams persisted progress snapshots as `progress` SSE events. It sends the latest snapshot on connect/reconnect, then polls at `artverse.scheduled-manga.progress-poll-interval-ms` (default `1000` ms) until a terminal task state. A reconnect therefore resumes from current persisted state without relying on in-memory event history.
- `DELETE /api/chapters/{chapterId}/scheduled-manga/{taskId}` idempotently cancels tasks that have not started. Running tasks return `409`.
- `POST /api/chapters/{chapterId}/scheduled-manga/{taskId}/retry` requeues only `FAILED` panels for a `FAILED` or `PARTIAL_FAILED` task, preserving successful results. It enforces the same per-user active-task limit; `UNCERTAIN` panels are not retried because the provider may already have accepted and charged the request.

Requests are scoped to the authenticated user and chapter. Local times with daylight-saving gaps or overlaps are rejected so callers must resolve the time explicitly. Repeating schedules are not supported. Missing panel numbers are snapshotted at create time; the immutable input snapshot also contains the chapter version, storyboard, style, character/profile context, reference object keys, color mode, image size, model profile ID/model and prompt policy version. A SHA-256 hash is checked before execution. Changed inputs stop at `STALE_REQUIRES_CONFIRMATION`. The image provider profile ID and selected model are stored, never the credential.

The conversation agent receives `schedule_manga_generation`, which can only use the authenticated run's story/chapter and user. It may specify up to three chapter numbers in that story. Routing declares scheduled generation as a conversation capability, and other agents do not receive the tool. The model cannot provide a user ID. Its compact instruction tells it to call the tool for a clear scheduling request, answer feature questions without creating a task, clarify material ambiguity, use the configured timezone when no zone was supplied, and report the IDs returned by the persisted service. Authorization, chapter ownership, model profile, storyboard, idempotency and limits remain application checks.

The database contains two shared leased worker slots, one shared per-user permit, and one permit per provider profile/model. This caps scheduled image work globally, per user, and per provider/model across replicas. Each task is atomically claimed by one worker at a time. Panel failures are isolated, with at most three provider attempts for retryable HTTP 429/5xx responses; the worker respects `Retry-After` and otherwise uses exponential delay with jitter. A process restart while a provider call was in flight marks that panel `UNCERTAIN`, avoiding an automatic duplicate charge. Existing immediate generation and SSE endpoints are unchanged; scheduled execution reuses their prompt policy, provider client and image storage path.

The schema is introduced by `V47__scheduled_manga_generation.sql`. Business task and panel states, snapshots, leases, shared worker slots and result image references are stored in PostgreSQL. `UNCERTAIN` outcomes require manual review and are excluded from the retry API. Batch requests create one persisted task per selected chapter, up to three chapters per request.

## Verification and implementation notes

- `mvn -q -DskipTests compile` passes.
- Focused service, API identity, retry classification, Agent tool routing/registration and persistence integration tests pass. `ScheduledMangaPersistenceIntegrationTest` runs against PostgreSQL, verifies Flyway/JPA schema compatibility, concurrently races two claimers, exercises lease takeover/fencing-token increment, and checks shared worker slots and scoped permits.
- Flyway validated all 47 migrations and applied V47 to the configured PostgreSQL test database. The Spring context initialized with `ddl-auto: validate`.
- A full `mvn -q test` run is not green in this checkout: AgentScope harness tests fail on null mock events, and ApiKeyService tests fail because the test encryption key is missing (with one unfinished Mockito stub). Testcontainers also cannot detect a valid Docker server response, but the configured local PostgreSQL integration path is available and passed.
- A separate scheduled-task SSE endpoint emits current durable snapshots on connect/reconnect; it does not alter the existing immediate-generation SSE route. Task preparation snapshots are assembled at request time, so no later billable prewarm phase is used. The lifecycle coordinator is deterministic application code; the conversational Agent only interprets intent and creates tasks through the restricted MCP tool.
